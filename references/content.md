# 文案与数据格式

来源：Ant Design 文案规范、数据格式规范；GitHub Primer 的 saving、empty-states 指南。

## 文案原则

- **以用户为主体**：写用户能做什么，不写产品为用户做了什么。只有在用户向平台反馈或申诉时，才用「我们」（例如「我们会在 3 个工作日内审核你的申诉」）。
- **称呼用「你」，不用「您」**，保持亲近感。（ToB 金融、政务等场景如果有既定规范，以既定规范为准。）
- **精简**：不重复用户已经知道的信息，也不写正确的废话。比如「姓名」输入框的占位文字写「请输入姓名」就是废话。占位文字应该给示例或格式，比如「如 张三」。
- **一致**：同一个事物全站只用一个叫法；操作按钮的名称要和目标页面的标题一致；按钮叫「发布」，成功提示就说「已发布」。
- **重要信息放前面**：用户第一眼就能看到结论，不需要在段落里找。
- **按钮用明确的动词**：「创建」「保存」「删除」「更新」。在可能产生歧义时带上对象，比如「删除仓库」，不要只写「确定」「提交」。
- **用词规范**：「其他」不写「其它」，「登录」不写「登陆」；「抱歉」只用于系统造成的问题，用户自己的操作失误不道歉。
- **语句**：中文用全角标点；中西文之间的间距交给 `text-autospace` 处理（见 foundations）。

## 错误与空状态文案

- 错误要说清三件事：**哪里错了、为什么、怎么改**。例如「表单未提交：3 个必填项为空」。
- 不写含糊的「出了点问题」，也不写过于技术化的「US-East-2 数据库集群故障」。错误码只在用于排查时才展示。
- 空状态分三类，写法各不相同：
  - **从未使用**：说明这个功能是做什么的，并给一个主操作，比如「创建第一个项目」。
  - **暂时为空**：说明这是正常情况，比如「没有新的通知」。
  - **加载失败**：说明出了什么问题，并给出恢复路径，比如「重试」或「查看状态页」。此时不要用俏皮的插画。
- **用户确实创建过的内容加载失败时，不能显示成空状态**，否则用户会以为数据丢了。要明确写「暂时无法加载」。

## 数据格式（中文默认）

| 类型 | 规则 | 例子 |
|---|---|---|
| 数值 | 默认加千分位；单位用小写；表格里数值**右对齐**，单位放在表头 | 123,220 kg |
| 百分比 / 进度 | 百分比保留到需要的精度；进度可以用分数 | 12.32%、12/30 |
| 金额 | 货币符号或代码加数字，保留两位小数；大额用「万」「亿」 | ¥123.00、CNY 1,123.00、3.2 亿 |
| 日期 | `yyyy-mm-dd`；范围用「～」，两侧加空格 | 2026-11-03 ～ 2026-12-01 |
| 时间 | 默认 24 小时制 `HH:mm:ss`；日期和时间之间用空格 | 2026-11-03 14:08 |
| 相对时间 | 1 分钟内显示「刚刚」，1 小时内显示「N 分钟前」，24 小时内显示「N 小时前」，再早显示 `mm-dd HH:mm`，跨年显示完整日期 | 3 分钟前、11-02 08:00 |
| 无数据 | 用 `--` 表示，不留空，也不写 0 | -- |
| 加载中 | 内容区用骨架屏 | |

- 相对时间旁边，悬停时要能看到绝对时间（用 `title` 属性或 `<time datetime>`）。
- 面向多语言用户时，用 `Intl.NumberFormat`、`Intl.DateTimeFormat`、`Intl.RelativeTimeFormat` 按地区格式化，不要手写格式。

## 敏感信息脱敏

| 类型 | 规则 | 例子 |
|---|---|---|
| 姓名 | 两个字时保留首字；三个字及以上保留首尾 | 张\*、张\*明 |
| 手机号 | 保留前 3 位和后 4 位 | 186 \*\*\*\* 1402 |
| 邮箱 | 保留前 3 位和域名 | 123\*\*\*\*@163.com |
| 地址 | 保留省市区 | 浙江省杭州市西湖区 \*\*\*\* |
| 金额等高敏信息 | 全部隐藏 | \*\*\* |

点击后才显示完整信息的设计，要提供明确的「显示 / 隐藏」切换，并且这个切换要能被读屏软件识别。

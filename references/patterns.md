# 交互模式：反馈、加载、保存、表单、空状态、降级、渐进披露

选择反馈组件、制作保存和表单流程时读取本文件。需要异步实现时进入 [异步反馈骨架](async-feedback.md)，出处见 [来源索引](sources.md)。

## 1. 反馈：按打扰程度选组件

原则：每个操作都要有反馈，但**能直接看到结果的简单操作，可以不额外提示**。反馈要即时，打扰程度要和信息的重要性相匹配。

| 层级 | 组件 | 用于 | 行为 |
|---|---|---|---|
| 最轻 | 行内状态变化 | 简单操作，结果直接可见 | 不额外提示 |
| 轻 | 全局轻提示（Message / Toast） | 操作成功、不重要的失败 | 顶部居中或角落显示，约 3 秒后自动消失，不打断操作 |
| 中 | 行内提示（Inline message） | 表单校验、局部问题 | 紧贴相关区块，**不自动消失**，用户修正后才消失 |
| 中 | 横幅（Alert / Banner） | 和当前页面相关的说明或警告 | 固定在页面或区块顶部，不自动消失，可以关闭 |
| 重 | 通知（Notification） | 系统主动推送的全局事件 | 角落显示，可以带操作按钮 |
| 最重 | 对话框（Dialog） | 必须处理的重要结果、不可逆操作的确认 | 阻断操作。只在信息重要并且需要用户操作时才用 |

- **重要的失败不要只用 3 秒的 Toast**，否则用户很容易错过。改用横幅、行内提示或对话框。
- 带操作 Toast 的停留、暂停和恢复路径见 [可信恢复](#10-加载通知与可信恢复)。
- 消息状态统一为 6 种：信息、成功、警告、严重错误、不可用（降级）、升级提示。每种状态都要**同时用颜色和图标**表达，不能只靠颜色。
- 徽标：重要且和用户相关的信息用数字，次要的用红点。
- Tooltip 只放简短的描述性文字，不能放链接和按钮；需要放操作时改用 Popover。
- 工具栏 Tooltip 可共用 Radix Provider；其默认首次延迟 700ms、组内跳过延迟窗口 300ms，产品改值须记录。验收键盘可获取、连续浏览不反复等待；触屏关键功能不依赖 Tooltip。

## 2. 危险操作：能撤销就不要确认

- 优先做成**可撤销**：先执行，然后在 Toast 里提供「撤销」。这比每次都弹确认框更顺畅。
- 不可逆操作（删除仓库、清空数据）才用确认：
  - 轻量的用气泡确认（Popconfirm），弹在按钮旁边。
  - 影响大的用对话框，标题写明要删的对象，确认按钮写「删除 xxx」，用危险色。极其危险的操作，要求用户输入对象名称后才能确认。
- 确认对话框的默认焦点放在「取消」上。

## 3. 加载

| 等待时长 | 做法 |
|---|---|
| < 300ms（项目默认延迟） | 立即显示按下反馈，暂不显示加载指示 |
| 300ms ~ 2s | 不确定进度的指示：小范围用 spinner，大面积内容用骨架屏 |
| 2s 以上 | 加上说明文字（正在做什么） |
| 约 3s 以上且能估算进度 | 用确定进度的进度条或百分比 |
| 很长 | 提供「取消」，允许后台运行并在完成时通知 |

- 骨架屏的形状要接近真实内容，避免加载完成后布局跳动；内容到达时，用淡入替换，不要硬切。
- 乐观更新的适用范围和并发回滚见 [实现骨架](async-feedback.md#乐观更新与回滚)。
- 优先使用组件自带的加载状态，不要每个页面各写一套。

## 4. 保存

- **默认用显式保存**（点按钮或按 Enter 提交）。同一个表单内不要混用显式保存和自动保存；同一个页面上的多个表单，最好也不要混用。
- 文本框、复选框组、单选框组、原生下拉框这类声明式控件**不要自动保存**：读屏用户用方向键浏览选项时，会意外触发选择；修改密码这类内容也可能被误提交。开关（toggle）可以即时生效。
- 保存失败时，**保留用户已填写的内容**，并就近说明原因。
- 有未保存的修改时，用户离开页面要提醒（`beforeunload`），站内路由跳转也要拦截。
- 按钮层级：保存整页用主按钮；只保存某一段时用次按钮；保存和取消并排时，保存用主按钮，取消用次按钮。
- 长表单或复杂流程，要提供分步保存或自动保存草稿，避免误操作丢失大量内容。

## 5. 表单

- **标签始终可见**。不要用占位文字代替标签：用户一开始输入，占位文字就消失了。
- 标签放在输入框上方（最适合扫视和移动端）；只有在密集的设置页里，才用左对齐的侧标签。
- 必填和选填，只标其中较少的那一类。
- **校验时机**：失焦时校验格式；提交时校验全部字段，短表单把焦点移到首错；长表单多错误先聚焦含数量和字段链接的摘要；修正后立即清除这条错误。不要在用户刚开始输入时就报错。
- 错误信息放在字段下方，帮助与错误的可访问关联按第 11 节同步。
- 选择合适的输入类型（`type="email"`、`inputmode="numeric"`、`autocomplete="..."`），让移动端弹出对应的键盘，并支持自动填充。
- **不要让用户重复输入**同一流程里已经填过的信息（WCAG 3.3.7）。比如收货地址可以一键复用为账单地址。
- 同一类内容使用同一种控件。不要一会儿用下拉框、一会儿用单选。
- 根据复杂度选择布局：
  - 字段少：单页平铺。
  - 字段多且能分组：分组表单。
  - 有明显先后顺序：分步表单，最后一步提供确认页，结束后给出明确结果。
- **设置页**：每页只用一种生效模式（即时生效或提交生效）。建议按任务关联分组；独立任务可用页签，不以数量硬切。用真实设置项验证用户能找到目标、理解归属且不漏保存。
- 登录和验证（WCAG 3.3.8）：允许粘贴密码和验证码，支持密码管理器，不要求用户做记忆或计算类的验证。

## 6. 空状态

结构和三类基础文案见 [文案](content.md#错误与空状态文案)。细分原因为首次使用、筛选为空、任务完成、无权限、待配置、系统错误，分别给创建、清筛选、返回工作区、申请权限、配置、重试入口；不要无权限时提示创建。

## 7. 错误与降级

- **不要掩盖问题**。明确告诉用户哪里出了问题，并尽量引导他们绕过去。
- 先区分**主要体验**和**次要体验**。主要体验不可用时，显示错误页；只是次要体验不可用时，正常渲染页面，只把受影响的部分换成简短的错误提示。
- 全局性故障：在页面顶部（全局导航之上）显示横幅，说明情况，并链接到状态页。
- 局部故障：受影响的块换成「警告图标 + 一句说明」。如果页面上同时出现太多警告，会显得整页都坏了，这时考虑直接隐藏次要模块。
- 网络断开时显示细横幅，并明确离线操作是否排队。
  联网线索与同步确认按 [恢复合同](async-feedback.md#真实进度旧数据和取消)，不要因 Wi-Fi 恢复就写已保存。

## 8. 渐进披露

- 只在确实需要收起信息时使用，不要为了「看起来简洁」把常用内容藏起来。
- 展开时保持用户的上下文：原地展开，不要跳页面，也不要让滚动位置大幅跳动。
- 展开控件要配文字，不要只放一个图标，比如「显示 12 条更早的评论」。
- 用 chevron 表示折叠或展开，不要用它表示翻页或「前往」。下拉菜单用 caret（▾）。
- 用 `<details>`/`<summary>` 或带 `aria-expanded` 的按钮实现，动画写法见 `motion.md`。

## 9. 新手引导

- 优先通过空状态和就地提示来引导，少用一上来就盖住整个页面的多步导览。
- 引导可以跳过，跳过后不再反复弹出，但要能从帮助入口重新打开。
- 帮助入口在每个页面上的位置保持一致（WCAG 3.2.6）。

## 11. 表单的结构与并发

### 提交与字段关系

- 普通资料表单允许提交后解释缺项，请求开始后再防重复。
  验收用户能发现缺少哪些字段；不要预先禁用一个没有原因的提交按钮。
  AI 空消息、无权限命令和危险前置条件属于不同场景。
- 用 fieldset/legend 给单选或复选组命名，选项仍有自己的 label。
  用读屏确认组名和选项名都可获取；不要用装饰分隔线代替组标题。
- 将错误视觉状态与 aria-invalid 同步更新。
  aria-describedby 同时引用帮助和错误；修正后清理过时错误，不覆盖长期帮助。

```html
<fieldset>
  <legend>通知方式</legend>
  <label><input type="checkbox" name="notify" value="email">邮件</label>
</fieldset>
<label for="email">邮箱</label>
<input id="email" type="email" aria-invalid="true"
       aria-describedby="email-help email-error">
<p id="email-help">用于接收通知</p>
<p id="email-error">请输入有效的邮箱地址</p>
```

### 数字、自动填充与校验

- 邮编、账号、验证码等标识符使用 text 配 numeric 键盘提示，并按业务验证长度或 pattern。
  验收前导零和粘贴；不要用 type=number 使标识符变成可步进数值。
- 金额允许小数时可用 decimal，但仍需解析和验证。
  验收设备上的负号、小数键和粘贴内容；inputmode 不负责验证。
- 多地址使用独立 section 的 shipping/billing autocomplete；验证码使用 one-time-code。
  验收完整粘贴与密码管理器填入；不要逐键拦截或让两个地址错误互填。
- 修正自定义错误时调用 `setCustomValidity('')`，提交检查实际 validity。
  服务端仍须再次验证；不要只清红框却遗留会阻止提交的自定义错误。

### 异步校验

- 建议每个字段用独立递增版本，只接收当前输入的结果。
  用旧请求晚于新请求返回的顺序验收；不要以为 abort 能代替版本判断。
- 可试用 300ms 防抖，用户首次输入未完成时不立即报错。
  测试输入法确认和快速改写；不要让旧“已占用”覆盖新“可用”。

```js
let version = 0;
async function validate(value) {
  const seq = ++version;
  const result = await check(value);
  if (seq !== version) return;
  renderValidation(result);
}
// 每次输入变化（包括清空）都先让旧版本失效，再安排校验。
// 请求失败只为当前版本显示可恢复错误，不谎报字段已通过。
```

### 幂等与条件字段

- 建议一次逻辑提交只生成一次 `crypto.randomUUID()`，网络重试复用同一键。
  修改参数或明确开始新操作才换键；验收服务端合同确实按键和参数去重。
  不要把前端按钮禁用当成服务端幂等。
- 条件字段不再适用时禁用其 fieldset，让它退出原生校验与提交。
  草稿另存，重新启用时恢复说明和校验；不要仅 display:none 留下隐藏必填项。
- 批量结果与上传阶段按 [复杂组件](complex-components.md) 展示，不另造反馈模式。

# 整页一致性与像素级验收

任何新建或大改界面的任务都读本文件：动手前写全局合同，交付前跑整页普查。
它管的是「各区块合起来是否像同一个产品」，以及每个盒子是否精确落在该落的位置；单个组件的做法仍在各专题。

本文件的上限均为建议默认，来自本项目的浏览器实测，不是外部标准；偏离时写进方案单的「例外」。

## 为什么单独成篇

逐条清单只能证明每个局部合规，证明不了整体协调。一次实测：一个完全按本规范独立完成的落地页，
单个区块都合格，整页量下来却是：区块上下留白 3 种组合、同级标题 3 种字号、全页 13 种字号且过半文字只有 12px、
直角按钮和圆角控件并存、有一个区块的左边线比其余区块偏了 64px。每一处单看都说得通，合起来就是不协调。

所以规则换一个方向定：先定全局，再做局部；验收靠测量，不靠目测。

## 1. 先写全局合同，再写任何区块

合同是一张表，写在 token 文件里。区块只能引用合同里的值，不能写裸值。

| 维度 | 合同里写死什么 | 默认上限 |
|---|---|---|
| 容器与对齐线 | 内容最大宽度、每个断点的左右边距、允许的缩进线 | 主对齐线 1 条，缩进线至多 1 条 |
| 区块节奏 | 每个断点的区块上下留白 | 2 种：标准、紧凑 |
| 字号角色 | 每个角色在每个断点的字号、行高、字重、字距 | 界面角色 6 个，显示角色 3 个 |
| 间距阶梯 | 允许出现的间距值 | 全部为 4 的倍数；光学例外至多 2 个且有名字 |
| 圆角 | 圆角档位，以及哪类元素用哪一档 | 3 档，另加全圆；同类控件同一档 |
| 控件 | 高度档、水平内边距、字号 | 高度 3 档 |
| 描边 | 宽度与颜色角色 | 宽度 1 种 |
| 动效 | 时长档与缓动 | 时长 4 档 |
| 色彩 | 文字色角色、表面角色、强调色用在哪里 | 强调色只给主操作和少量标记 |

- **同一角色，全页一个值。** 两个区块的二级标题就是同一个角色，不能一个 44px 一个 50px。
  确实需要不同时，它是一个新角色：起名字、写理由、计入上限。
- **流式字号按角色定义一次。** 用 clamp 时公式写在合同里，区块不各写各的；在每个目标视口上结果要落在整像素。
- **区块留白只从合同里选。** 首屏和收尾区可以用紧凑变体，但不能出现第三种组合。
- **所有区块共用主对齐线。** 带底色的满宽区块，其内容仍回到主对齐线；需要缩进时用合同里的那一条缩进线。
- **改一个值之前先问：它在合同里吗。** 不在就先改合同，再让所有引用处一起变。

## 2. 层级落差

局部最容易失衡的地方是大标题和它旁边的文字。

- 紧挨显示级标题的说明文字用正文或导语角色，不小于 1rem；不要在 48px 的标题旁放 12px 的说明。
- 最小字号角色只给标注、编号和元信息。按字符数计，12px 及以下的文字默认不超过全页的 25%。
- 正文角色应当是全页字符数最多的角色。做不到说明页面在用标注冒充内容。
- 每一屏只有一个视觉重心。大片留白要有意图：它在衬托什么。说不出来就是内容没撑起版面。
- 强调色在一屏内出现的位置越少越有力。先数一数，再决定要不要加。

## 3. 像素级规则

- **有可见边界的盒子落在设备像素上。** 有底色、描边、阴影的盒子，以及图片和画布，其左边界、宽、高乘以设备像素比后应为整数。
  常见成因：奇数宽容器对半分、百分比列宽、未取整的 clamp。修法是让容器宽为偶数，或用网格间距吸收余数。
- **滚动条不改变布局宽度。** 滚动容器加 `scrollbar-gutter: stable`，避免出现滚动条后整页多出半像素。
- **描边保持 1 CSS px。** 不用 0.5px 做「更细的线」；要更轻就降低颜色对比。
- **位图够清晰。** 位图的固有像素不小于显示宽度乘以设备像素比，默认按 2 倍屏准备，或提供 srcset。
- **图标盒子是整数尺寸**，光学居中用有名字的偏移量，不逐个手调。
- 只由文字撑开的盒子天然带小数：没有可见边界的不计入以上检查；带底色的行内标签只记为提示，放大看一眼边缘即可。

## 4. 普查：用测量代替目测

交付前在真实浏览器里对每个目标视口跑一次 [普查脚本](../assets/page-census.js)：
把文件全文粘进控制台，或用自动化工具的 eval 执行。它只读页面，返回一个对象。

| 输出 | 看什么 |
|---|---|
| findings | 超出默认上限的条目。目标是空数组；留下的每一条都要写进「例外」并说明理由 |
| notices | 不算超限、但要人看一眼的提示，例如出现第二条对齐线、行内标签宽度带小数 |
| sections | 每个区块的上下留白、文字最左边界、标题字号：横向一比就能看出谁不合群 |
| type | 实际字号分布、小字占比、字重和文字色的种类 |
| spacing | 实际出现的间距值，以及不在 4 的倍数上的值分别出自谁 |
| shape / motion | 圆角档、控件圆角与高度档、描边宽度、过渡时长档 |
| pixel | 未落在设备像素上的盒子数量与样本、分辨率不足的位图 |

- 至少跑两个视口：桌面（默认 1440×900）和窄屏（默认 375×812）。
- 等页面稳定再跑：先把整页滚一遍，让懒加载的图片和延迟初始化的画布就绪。没加载的图、透明度为 0 的元素不会被量到，跑早了会少报。
- 同一标签承担不同字号角色时（章节标题和收尾宣言都是 h2），在元素上写 `data-type-role`，脚本按角色比对，不为过检查牺牲语义。
  控件同理：脚本默认分全圆、文字操作、有底或有框三类比对圆角，需要更细时用 `data-control` 声明类别。
- 开工时先确认能不能打开真实浏览器。不能就写进方案单，交付状态记为「源码已交付，验收未完成」，不等到最后才发现。
- 普查结果和合同对不上时，改页面，不改合同来迁就页面。
- 脚本判断不了审美，只负责把「不一致」变成数字。数字干净之后再做下一节。

## 5. 整页评审

- 留三张实图：桌面首屏、桌面整页（长图或逐屏）、窄屏首屏。素材拼图不是页面截图。
- 把整页缩到约四分之一大小看：区块的明暗和疏密是否有节奏，强调色是否扎堆，有没有哪一屏突然变了风格。
- 相邻两屏并排看：标题位置、边距、控件形状是否同出一辙。
- 打不开浏览器时，本节和上一节都记为「未验证」，不得用源码推断通过；并在报告里写明阻碍。

## 6. 例外怎么记

每条例外写四项：偏离了合同的哪一行、用在哪里、为什么这里必须不同、影响范围是否只限这一处。
「看起来更好」不是理由；理由要能说出它服务的内容或读者。同一维度的例外超过两条，说明合同该改了。
